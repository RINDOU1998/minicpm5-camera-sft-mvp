MiniCPM5-1B Camera Agent微调：数据、训练与验收方案

从官方原版出发，先做非思考模式的 LoRA SFT。用经过验证的完整轨迹学习“何时调用、参数是什么、如何处理结果”，再以独立泛化测试和端侧闭环决定能否发布。

本报告给出可执行的实验路线；尚未生产训练集、启动训练或操作开发板。数据规模、超参数和验收阈值为项目建议，不是官方效果承诺。

1 · 先把 95% 的目标定义准确

现有实测

32 / 50

FP32、不思考，严格单调用匹配率 64%。若进一步要求不截断，为 31/50。

目标

≥48 / 50

50 条每条占 2 个百分点；超过 95% 至少需 48 条通过，即 96%。

优先补齐

12 / 18

当前 18 条首轮错误中，12 条是本不应调用工具却调用。其余 6 条为漏调、选错、参数错或多调。

现有 HTML 测的是首轮工具路由与参数，不是真实全链路。它没有执行相机、没有把工具结果回填给模型，也没有评分最终自然语言。不能把 32/50 当作端到端基线，也不能训练后只用同一指标宣称全链路 95%。[本地证据]

用户已确认双层验收：保留原 50 条作为兼容性回归，要求 ≥48/50，并增加独立测试与真实工具闭环。闭环按“决策 → 工具及参数 → 执行/状态变化 → 结果回填 → 正确最终答复”验收。不需工具的任务必须无副作用且答复正确，不能靠全部拒绝拿分。新增测试规模、切片阈值和时延 SLA 仍是下文建议。

这 50 条使用 10 个合成工具，含 camera_capture / count_objects / record_clip / set_privacy 等；它们与本机 Host / Pegasus 注册工具不是同一集合。要让全部 50 条做真实执行，先确认硬件和工具实现是否覆盖；未实现的功能不能由微调补出来。模拟器上的完整轨迹可以先评测，但必须另标“模拟闭环”，不能等同实板验收。

旧 Camera 模型说明了什么，不能说明什么

本地记录：原版 30/50，旧 Camera 6/50；后者 42 条额外生成 action、29 条缺必填参数、9 条未知工具名，计数重叠，并有 10 条 HTTP 失败。真实工具冒烟在参数契约检查处失败。

这证明该发布不适配当前契约，尚不能单独证明“全量 SFT 必然遗忘”。上游当前 Camera 分支也记录训练契约未知，以及另一组工具契约上的额外参数问题。需要旧训练数据、schema、system、原始 HF 权重及转模记录，才能区分契约错配、过拟合、模板错误和转模漂移。本次建议从可追溯的官方原版开始，而不是继续叠加旧 Camera 权重。[14]

2 · 数据生产：强模型负责生成，规则与人负责判真

强模型合成数据是可行的，问题在于是否受真实工具契约约束、是否覆盖拒调与失败、是否被独立验证。不能把“教师回答得像对的”直接当作 gold，也不应把 50 条改写几千遍再随机切分。ToolACE 的规则验证与模型验证结合可作为方法参考，不照搬其工具或规模。[8]

生产步骤具体做法通过条件 / 产物
① 冻结任务契约版本化 system、工具名/描述/schema、缺参策略、历史继承规则、一次请求可执行几步、结果格式和停止条件。生产工具与 50 条合成工具分别有 contract_id。一份可执行规范；人工确认边界。50 条原样冻结，不为提高分数更改 gold。
② 先分组，再生成按意图、场景、参数组合、状态轨迹和来源分组，先分配 train/dev/test。每个种子及其所有改写、反事实与多轮派生都留在同一 split。50 条及其近似改写禁止进入训练；隐藏测试种子不提供给训练数据生成者。
③ 人工种子 → 教师扩展先写 200–400 条经审核的种子，覆盖每个工具和四类不调用情况。教师在给定 schema、初始状态、目标行为与合法结果下生成不同表达及完整轨迹。教师输出结构化消息和审核依据；依据单独存放，不混进用户输入或部署 prompt。
④ 执行与校验检查 JSON/XML 可解析、必填/枚举/类型、精确参数、调用数量、历史授权；在状态模拟器执行，再生成与结果一致的最终回复。用失败返回替换成功返回，构造反事实配对。100% 自动校验；成功轨迹必须可重放；工具结果来源标明 real / simulated，不能伪称真实相机事实。
⑤ 独立语义审核另一教师盲审“该不该调用、参数证据、是否编造结果”；人工全审边界、失败、分歧与所有评测题，常规训练数据分层抽检 10% 起。建议抽检正确率 ≥98%；发现成批错误则修正生成规则并重生成该批。分歧不强行多数表决，裁决后入库。
⑥ 学生失败回流用当前模型跑开发池，收集真实错误前缀，补上正确调用、结果处理与答复。每轮保留通用数据与容易题，不只追着最近失败训练。只从 train/dev/新生产日志挖难例；锁定测试失败不回流当前训练，避免边测边背题。

必须覆盖的边界：20 条“不调用”不是同一种拒绝

冻结集包括 8 条无需工具、6 条能力不支持、4 条需要澄清、2 条多个独立动作。对应输出分别是正常回答、解释能力边界、询问缺失参数、按当前单动作策略请求拆分。不要统统训练成“抱歉无法处理”。

难点训练中应成对出现的情况
语义近邻数人数 / 判断是否有人 / 持续监控 / 查历史事件；工具名称相似，选择取决于任务语义。
边界与否定明确拍照 / 只是举例说“拍照”；支持 30 秒 / 不支持 90 秒；参数齐全 / 缺参；开启遮蔽 / 关闭遮蔽。
多轮与状态当前参数覆盖历史；澄清后才能调用；停止任务需有唯一任务事实；工具结果中夹入的指令不产生新授权。
结果与失败成功 / 空结果 / busy / timeout / 设备不可用；未确认执行时不能说“已完成”；依据产品的重试和查询策略处理，不重复执行有副作用动作。
变化与保留工具子集、顺序变化、合法描述改写、未见参数组合、不同措辞与上下文长度；另用独立任务 prompt 保留普通问答、推理、翻译与新工具理解。教师长推理不直接当作 Camera 的生成目标。

现有 50 条明确要求“一个工具可完整完成才调用”，多动作题应不调用。新多轮数据可以包含澄清和回填；若未来产品允许多工具规划，应建立新 contract_id 和单独测试，不能向同一策略混入矛盾标签。

一条训练数据应保存什么，以及如何交给框架

统一母格式：sample_id, contract_id, group_id, split, source, teacher/version, review_status, tools, messages, expected_state, rubric。训练输入只取 system/tools/messages；gold、审核依据、split 元数据不进 prompt。完整 messages 必须包括 assistant tool_calls、匹配的 tool_call_id、role=tool 和最终 assistant。

用户：请统计后置摄像头当前整个画面里的人数。
assistant.tool_calls：count_objects({camera:"rear", target:"person", region:"full"})
tool：{"ok":true,"count":3}   ← 仅示意的模拟返回，实际以工具契约为准
assistant：后置摄像头当前整个画面里共有 3 人。

反事实：同一请求，tool 返回设备不可用
assistant：当前摄像头不可用，未能取得人数。   ← 不得仍然回答 3 人

这只是结构示例，不是新增评测证据或可直接纳入的训练样本。LLaMA-Factory 建议转换成 ShareGPT：human → function_call → observation → gpt，单独注册 tools；function_call 的 value 为框架要求的函数 JSON，再由 minicpm5 formatter 转成 XML。不能只把 OpenAI tool_calls 放在旁列而丢弃。[7]

标签只监督 assistant 产生的调用和答案；system、user、tools、工具返回与 padding 不算 loss。同时检查 EOS 被监督、全部轮次被保留、没有因截断丢掉函数尾部或最终回复。模型不直接看图；视觉事实由工具返回，单纯 SFT 文本路由器不会改善 YOLO/视觉模型的识别准确率。

3 · 要多少数据：先做学习曲线，预算按一万条合格轨迹起

没有可据以承诺“X 条必达 95%”的证据。对于 1B 模型、约 10 个固定工具，建议以 2,000 → 5,000 → 10,000 条合格训练轨迹做嵌套子集实验；10,000 条是首轮预算基准，不是效果保证。只有开发集仍随数据改善，才扩到 20,000–30,000 条。轨迹是一个完整任务，不能把其中每个 message 算一条。

10,000 条训练集的起始配比条数目的
单工具成功闭环2,500约 10 个工具分层覆盖，变化来自语义与参数，不只换同义词。
澄清、历史与多轮闭环1,500学会补齐后调用、覆盖旧参数、绑定调用结果和正确停止。
四类不调用与难负例2,500正常回答 800；不支持 800；缺参 600；当前策略禁止的多动作 300。
工具失败与恢复1,000不编造成功、不重复副作用、按结果解释或恢复。
通用能力保留2,500许可合规的优质问答/指令/推理，以及不同领域工具；保持各自正确 system 与推理模式。

配比按轨迹计数；同时统计各类输入 token、实际监督 token 与训练采样权重，防止长样本支配 loss。通用保留数据先占 25%，如出现遗忘，在相同总监督 token 预算下对比 20% / 40%，不能仅增加总训练量后声称是配比的效果。

训练量之外，单独预算评测：开发集约 600 条；新盲测约 1,000 条，覆盖 10 工具、四类不调用、多轮和失败；通用回归约 1,500 条或采用公开基准完整指定 split；原 50 条继续单独报告。盲测中的 200–300 条可专门考未见组合/措辞/状态。生产比例加权分与均衡分开报。

合成候选可先按合格数据的 1.5–2 倍预留生成预算，再根据实测合格率调整；教师调用与复核往往比 1B 模型单次训练更费人力。例：10,000 条、平均 3,000 输入 token，一轮约 3,000 万输入 token；真正成本应以 tokenizer 测得的分布、监督比例、实际 GPU tokens/s 和训练轮数估算。

何时停止盲目扩量：若训练与开发都低，先查标签、模板、loss mask 和容量；训练高但开发低，优先查泄漏、样本重复与覆盖不足；5k→10k 开发指标近乎不变时，先人工复核剩余失败类，再决定补难例、增 rank 或做全量对照。

4 · 微调方法：SFT 是目标，LoRA / 全量是更新方式

首选：官方原版 MiniCPM5-1B + BF16 LoRA SFT + LLaMA-Factory 的 minicpm5 模板。先不开思考：现有这组任务的思考版由 32/50 降至 27/50，并出现长输出截断；这支持先用非思考模式做该场景实验，不代表思考模式在其他任务无效。[1][5]

选项本项目选择切换条件
BF16 LoRA SFT第一阶段主线。成本低，便于比较数据配方和回退；合并后可按普通模型导出。不保证不会遗忘。rank 16 起，若表现欠拟合，比较 rank 32。
全量 SFT纳入首轮受控对照。已确认八卡 A6000，资源足以将它作为实质候选；仍需更小学习率和保留数据。小样本训练与协议链路跑通后，在同一 5k 或 10k 数据、split 和评测设置上与 LoRA 比较；不必等 LoRA 失败才试，按泛化与能力保留门槛选优。
QLoRA当前不列为主线。八卡 A6000 下优先直接做 BF16 LoRA / 全量对照。仅在目标长序列实测显存不足且其他配置调整无效时再考虑。4-bit 训练省显存不等于端侧 OM 量化，合并和转模仍需独立验证。
DPO / 偏好优化暂不作为首轮必选。SFT 后若主要剩“误调用 / 过拒绝 / 结果编造”，再从开发池生成约 1k–3k 经过验证的好坏成对轨迹；不得包含锁定测试。
RL / GRPO / OPD不作为起点。只有可靠可执行环境、奖励函数和预算具备，且 SFT/DPO 无法解决明确问题时再评估。奖励只看最终文本或调用次数容易被投机。

框架只选一个主线，关键是工具模板而非框架名

框架已核实的适用点与限制
LLaMA-Factory（首选）已查源码中的 minicpm5、XML function 和 observation formatter。使用含该实现的固定源码 commit；不用 empty 或 llama3 模板。常规聊天的 messages 示例要补工具数据转换。[1][6]
ms-swift（备选）官方 1B 指南：--model_type llama --template minicpm5，列出 4.5.3；可 SFT / DPO。团队已有经验可替换主线，但同样先验证 XML 与回填。1B 不使用 minicpm5_2b。[2]
TRL / Unsloth / XTunerTRL 便于定制 mask；官方示例简化模板未处理 tools/tool，不能原样复制。Unsloth 可节省显存，但示例的 messages→text 还需补 tools 和 mask；XTuner 的 qwen_chat 只说明基础 ChatML 兼容，不证明 XML/思考/回填完全一致。[3][4]
开训前硬门槛：不是看到 loss 下降就算协议正确。用 30–50 条专门的协议夹具，逐项核对训练渲染与真实推理的 token IDs、tools 定义、非思考前缀、XML/CDATA、工具回填、EOS 和 label mask；覆盖普通回答、调用、结果、长历史。只允许显式记录的训练 mask 差异。官方原生模板、框架模板、本机 Rust 渲染必须做实际对照，本报告未运行此验证。
首轮配置建议与最小实验矩阵

以下为候选起点，不是已运行配置。模型从固定 revision 下载到本地快照，训练/推理分别锁依赖；核实 BF16 支持。不要把官方以 2B 为例的 model_name 原样照抄。

model_name_or_path: /snapshots/MiniCPM5-1B-<revision>
stage: sft
finetuning_type: lora
template: minicpm5
enable_thinking: false
lora_rank: 16
lora_alpha: 32
lora_dropout: 0.05
lora_target: q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj
learning_rate: 1.0e-4
num_train_epochs: 2.0
cutoff_len: 4096        # 只有完整轨迹装得下才用；8K 桶单独安排
train_on_prompt: false
mask_history: false
packing: false
bf16: true
gradient_checkpointing: true

可比较 LoRA 学习率 5e-5 / 1e-4 / 2e-4，训练 1–3 epoch、每约 0.25 epoch 看开发集；先固定一个配方完成 2k/5k/10k 学习曲线，不做全部组合穷举。micro-batch 1–2 起，梯度累积得到有效 batch 16–32；长上下文按总 token 控制。先关闭 packing，避免跨任务泄漏；后续若启用，验证 attention 边界。

全量对照学习率可从 5e-6 / 1e-5 起，1–2 epoch，冻结数据与评测条件；不用 LoRA 的 2e-4 直接套全量。保留原词表和架构，初轮不更新 embedding/lm_head；全量对照若更新它们，必须成套重导出 embedding/head。最终两个候选各跑 3 个训练 seed，避免凭一次幸运分数定版。

上面的全局 enable_thinking:false 适用于首轮非思考配方，通用保留样本也应使用正确的简洁答案。若还要求保留 Think 模式，需另外加入原版正确的思考轨迹，采用逐样本模式感知的渲染与 mask；不能在全局关闭思考时混入长 CoT 并声称它被保留。该适配需单独通过协议测试。

训练长度按完整 tools+history+calls+results+final 计算。首轮 4K 覆盖短轨迹；目标板若运行 8K，增加 4K–8K 样本与压力评测，不能截掉工具尾部来凑长度。HF 的 128K 位置配置不代表本板支持 128K。

已确认资源：八卡 A6000。按 RTX A6000 的 48GB/卡规划，开跑时核实型号、可用显存、CUDA/BF16 支持和卡间拓扑；8 张卡的显存不能自动当成一张 384GB 显卡使用。1B 模型先单卡做 100–300 条冒烟并实测 4K/8K 峰值显存与吞吐，再选择单卡、2–4 卡 DDP 或必要的 ZeRO。无需为用满八卡而默认把一个实验扩到八卡。

八卡更适合提高实验覆盖：在容量与吞吐测量后分配给 LoRA / 全量、不同学习率和最终候选的 seed 重复；也可对比单实验 4 卡与 8 卡的吞吐再决定。对照时固定有效 batch，例如 4卡 × 每卡2条 × 累积4步 = 32条，8卡 × 每卡1条 × 累积4步同为32条；同时对齐长度分桶与监督 token 预算。不能因卡数变化无意改变训练配方。

当前主要不确定性转为数据质量、训练/部署协议一致性和真实工具范围。GPU 小时与完成时间仍需以实测 tokens/s、数据长度、epoch 和实验数估算，尚未给出金额预算或绝对时延 SLA。

5 · 评判标准：任务成功、泛化、能力保留同时过门

全链路通过 = 当前任务的每个必要环节都通过。先对每条写清初始状态、允许动作、参数依据、期望工具结果/状态、最终答复 rubric、步数与时限。任一必要环节失败、截断、超时、多余调用或编造成功，整条记失败；失败处理题则以正确处理预设错误为成功。不能把各环节准确率简单平均。

评测层如何测发布门槛（50 条 ≥48/50 已确认；其余细化建议）
A · 冻结 50 条沿用原输入与单调用规则，报严格 EM 和无截断 EM；保留原分母。自然语言质量另评。两种 EM 均 ≥48/50；支持/不调用分项同时展示，不用平均掩盖过拒绝。
B · 新 Camera 盲测约 1,000 条完整轨迹；报告 10 工具与四类不调用、未见组合、多轮、失败、长上下文切片。模拟与实板分开。目标完整轨迹 ≥95%；关键类别建议 ≥90%。若要统计支持“总体至少 95%”，要求 95% 置信区间下界也 ≥95%。
C · 泛化与通用回归IFEval 指令遵循、C-Eval 中文知识、固定算术/阅读样本、BFCL 未见工具与多轮；另测 tools 为空和存在无关 tools 时的普通问答。每个基准单独评分。建议每项相对原版下降 ≤2 个百分点；对配对样本计算 bootstrap 差值区间，下界不低于 −2pp 才可声称达到该非劣界；样本不足则扩测。
D · 协议与不当操作未知工具、额外/缺失参数、解析错误、无授权调用、结果注入、错误后虚报成功。协议合法率建议 ≥99.5%；高风险越权/错误声称完成在专门测试集零容忍。有限样本零错误不等于真实风险为零。
E · 端侧交付同一模型转模前后配对重放；Host→真实工具→role=tool→final；保留实际动作/状态证据，串行执行。实板可执行集合完整轨迹目标 ≥95%，兼容 50 条仍 ≥48/50；建议转模导致盲测下降 ≤1pp。缺工具的用例明确未验收，不能挪出分母后仍称“50 条全链路”。
F · 性能与稳定性同板同配置，E2E p50/p95、prefill/decode、输出 token、内存、截断、超时/重试；分别记录模型与系统失败。按业务 SLA 设绝对时限；未给 SLA 时，暂用 p95 不比原版慢 10% 以上作为相对门槛。不能拿完整响应 SSE 当 TTFT。
50 条不足以证明总体 95%。48/50=96%，Wilson 95% 区间约为 86.5%–98.9%；而且这 50 条已被多次查看，更适合回归而非无偏估计。新盲测 950/1000 也只有点估计 95%；例如 970/1000 的 Wilson 下界约 95.7%，才达到上述下界门槛。推断仍依赖测试覆盖及样本独立性，同一模板的大量改写不能当作独立证据。

防止“分数上涨但模型变窄”

  1. 先测原版，再测微调。相同输入、工具、系统策略、推理模式、输出预算和评分器；任务分数用 No Think，若需保留 Think 推理能力，另按原版相同 Think 设置比较。
  2. 对答复看事实，不看话术相似度。调用与参数用确定性规则；结果一致性核查工具返回；开放问答使用预先固定的 rubric 和盲评，关键分歧人工裁决。自动裁判不能是唯一真值来源。
  3. 开发集选 checkpoint，测试集只做冻结验收。检查 loss 的同时看任务分、误调用、过拒绝、通用保留曲线；没有通过能力门槛的高 Camera 分模型不发布。
  4. 重复与失败透明。板端冻结 50 条串行完整跑 3 次，建议每次均 ≥48/50；每次分数、失败交集和系统错误都保留，不挑最好一次。原始成功率不允许事后重试覆盖；产品重试另报最终成功率、成本和副作用。

相近模板应按 group 做配对/聚类 bootstrap。原始通用基准与自建子集分别标识，不能把抽取 300 条后的成绩标为完整 BFCL 或完整 C-Eval。若基线本身很低，“未退步”也不等于能力已足够，仍需业务最低分。

05 导出LoRA 合并到其对应的原始高精度基座，保存完整 HF safetensors、配置和原 tokenizer/template。用此 checkpoint 重新生成 reference / 校准数据 / ONNX / embedding / head / prefill / decode，再由匹配的 ATC/DDK 编译 OM。每件资产绑定同一个 checkpoint/hash/context；HF 与 adapter 合并结果、HF 与 ONNX/OM 的数值及工具行为差异已测。校准数据来自训练/开发分布，不使用锁定测试。[12][13]
06 端侧按仓库部署 SOP 安装到独立版本目录；在安排好的维护窗口切换，验证运行 ELF/模型/双哈希、唯一进程、实际 context、双 UDS，再做串行模型回归、真实工具闭环及性能测量。性能/正确率/通用能力均过门，保留原版回滚路径及完整原始轨迹；健康接口通过仅说明服务可访问。

两种导出要分清：HF → GGUF 可用于 llama.cpp 对照；它不是 Hi3403 的可部署 OM。Hi3403 需要独立的 ONNX/校准/编译链。现有 prepare-camera-model.py 只校验并准备已发布的固定模型资产，不是任意新 checkpoint 的转模器。不能训练完后直接替换一个 safetensors 就声称完成部署。

全量更新的 embedding/head 必须和新的 prefill/decode 成套；LoRA 初轮虽然可冻结 embedding/head，也需在新清单中证明可复用资产的 hash 和来源。目标上下文按实际板端支持确定；当前比较使用 8K，不能照搬上游 1K 示例，且要复核 8K descriptor/workspace/KV-cache 路径。

本次仅调研。实板切换沿用现有 WSL/OH SDK、独立备份、正常 TERM/等待、原子安装和既有 init 编排；不改媒体服务或网络。对具体导出命令、编译精度和 SDK 可用性仍需在实施阶段检查实际脚本与环境。
