# Camera Agent 数据生产 MVP：先用 300 条跑通链路

本轮只做原路线的 1–3：冻结契约与基线、建立数据生产和评测材料、交付云端小样本试训代码。源码与后续文档迁入 `D:/workspace/minicpm5-sft`；旧 Pegasus 仓库保留原样。

## 先固定四项决定

1. 工具：现有 50 条 Camera 数据集中的 10 个工具，完整保留 system、工具说明和 schema。
2. 基线：官方 MiniCPM5-1B，固定 revision、BF16、No Think、greedy、128 token 输出上限。
3. 样本：300 条新轨迹，240 train / 60 dev；原 50 条是独立保留的回归材料，不参与训练。开发集不是隐藏盲测。
4. 目标：验证生产和训练链路；当前不以“300 条必达 95%”承诺效果。

## 数据从哪里来

**agent 写场景和候选，程序维护契约、标签、模拟事实和版本。** 本仓先交付 75 个 agent 编写的可审查种子，以四种受控表达扩成 300 条。只有表达前缀变化的样本不能算独立任务；它们全部与同源样本放在同一 split。相同工具参数组合进一步归为同组，实际共 73 组。

这是一批可复现的链路数据，不是最终高多样性语料。下一批可让 agent 按固定计划重写真实语句和场景，仍需通过验证和独立审核；不要通过换随机 seed 制造“全新测试集”。

| 类型 | train | dev | 合计 | 学什么 |
|---|---:|---:|---:|---|
| 成功调用与结果回填 | 120 | 40 | 160 | 10 个工具、参数、结果后的答复 |
| 工具失败与正确解释 | 36 | 4 | 40 | 不编造成功；MVP 使用 device_unavailable |
| 无需工具的正常问答 | 28 | 4 | 32 | 不被摄像头词汇诱发误调用 |
| 不支持的能力或枚举 | 28 | 4 | 32 | 不近似、不乱补工具 |
| 参数缺失/任务不明确 | 20 | 4 | 24 | 先澄清、不默认补值 |
| 多个独立动作 | 8 | 4 | 12 | 遵循当前单动作策略，请求拆分 |
| **总计** | **240** | **60** | **300** | |

本轮未覆盖：澄清后的完整追问流程、多类超时/重试、长历史、复杂状态模拟、系统性通用能力基准。这些属于扩量阶段，不能用当前通过结果替代。

## 最小生产链路

| 步骤 | 输入 | 输出 | 门槛 |
|---|---|---|---|
| 1 冻结 | 原 50 条及工具契约 | contract、原文件 SHA256、BF16 revision | 工具/system 与原样本一致 |
| 2 制定计划 | 人工/agent 审查的场景种子 | sample_id、group_id、split、标签与参数依据 | 同源及相同参数组合不跨 split |
| 3 生成候选 | 计划 + 工具契约 | messages JSONL | agent 不读回归题、不改变规定事实 |
| 4 规则校验 | 300 条候选 | 错误清单、相似性提醒、覆盖统计 | 无未知工具、缺参、多参、枚举错、轨迹错、精确重复/泄漏 |
| 5 语义复核 | 原始请求、工具、预期、验证结果 | 带 sample hash 的审核记录 | 独立审核应判断意图和事实；规则校验不能替代 |
| 6 冻结发布 | 候选、审核、split | train/dev、manifest、hash | 任何后续修改都能被识别；候选不能自称已审核 |
| 7 试训 | 官方 tokenizer、冻结数据 | 渲染证据、mask、adapter、完整评测日志 | 先验证 token，再在云端手动训练 |

## 验证器到底保证什么

**能机械检查：**10 工具原始契约、必填参数、字符串枚举、额外字段、精确标签、每个参数在请求中的规范词证据、停止任务的给定状态、tool_call_id、结果与模拟事实一致、最终参考答案不被改写、同组 split、文件 hash、回归题精确重复和词面相似性。

**不能自动证明：**一句改写是否偷偷改变意图、否定范围是否正确、答案是否足够自然、是否真实泛化。词面相似度低也不能证明没有语义泄漏。独立审核单独留状态，不用验证器绿色结果冒充人工认可。

现有 schema 的 `additionalProperties=true` 保留原文；验证器按历史严格 EM 口径另行拒绝额外参数，避免悄悄改变输入来提升分数。

MVP 工具返回为项目自定义 `mvp-simulated-v1`：只在精确匹配的调用后回填固定结果或错误。不声称是生产工具返回格式，也不触碰设备。停止任务复用原评测中的 `previous_tool_result/current_query` 表达。

## 两个清晰状态

- **链路试训：**规则通过但独立审核未完成；必须显式使用 `--smoke`，实验结果不得用于正式发布声明。
- **审核后数据：**每个样本都有匹配 hash 的独立 accept；`prepare` 去掉 `--smoke` 并提交审核文件。不因此自动获得模型效果或真实硬件验收。

本轮首批 300 条状态是前者。让另一个 agent 审核时要记录真实执行的身份与结论，不能把“准备让 agent 审核”填成 accept。

## 云端训练为什么这么小

八卡 A6000 先使用一张卡：BF16 LoRA rank 16、有效 batch 16、2 epoch。暂不增加全量 SFT、DPO 和分布式训练变量。

采用 Transformers + PEFT 小型训练器直接使用官方 chat template。一个 assistant 步是一个训练 example；工具返回作为下一步输入但不监督其 token。因此 240 条训练轨迹产生 396 个 assistant example，60 条开发轨迹产生 104 个。没有改词表，没有用简化聊天模板。

云端顺序：数据验证 → 固定模型下载 → tokenizer/mask 检查 → BF16 原版 dev/50 基线 → LoRA → adapter dev/50 → 合并 → merged dev/50 → 配对比较。完整可复制命令都在 [README](../README.md)，这里不重复维护另一套。
